# REIM 路线图

> 基线：Minecraft Java Edition 26.3 / UE 5.8.4 / Windows x64 首发。  
> 本文是 `ARCHITECTURE.md` §13 的展开，并作为**阶段顺序的权威说明**。路线以 M1→M2→M3→M3.5→M4 为主线；**M3.5** 是 M4 前的增补阶段（原生功能实现与 Java→C++ 转换），执行计划见 `M3_5_PLAN.md`；文中 `P0-A`…`P0-F` 只是可行性实验编号，**不是阶段名**。  
> 本文不提供日期或工期承诺。阶段是否完成只看验收条件与门禁，不看投入时间。

---

## 1. 原则

1. **可运行成果优先**：第一个核心目标是 **M1**——用 C++ Native Runtime 真实加载并显示 Minecraft 世界，而不是先做产品外壳或文档完备性。
2. **单一游戏实现**：临时 C++ Renderer 与 UE Renderer 共用同一个 C++ Runtime、同一份世界状态和同一套 Rendering Contract。渲染后端可以替换，**游戏逻辑不能出现两套实现**。
3. **真实数据**：原型必须读取用户自有 Java Edition 文件中的真实世界数据。临时渲染器只显示 Runtime 提供的状态，**不能内置或生成一套假世界作为成果**。
4. **产品边界不可漂移**：没有 javaw/classpath/JVM 游戏启动路径；唯一可启动目标是 Native Runtime。
5. **纵向切片**：先打通“加载真实世界 → 显示 → 移动 → 保存”，再扩广度；每个阶段都要有可运行、可展示的结果。
6. **差分驱动**：原版行为是规格；每个子系统必须有 oracle/harness/截图/存档往返。
7. **Converter 全程推进**：Converter 从 M1 启动，M2 并行扩展，M3 完善和规模化；它不是 M3 才开发，也不是“先做完通用转换器再开发游戏”。Converter 与 Runtime 从早期共同演进，生成代码、数据结构、运行时接口和版本信息保持一致；M1/M2 必须持续使用真实 Converter 产物验证 Runtime，不能长期依赖手写假数据或临时模拟数据。项目不做通用 Java→C++ 编译器；M3.5 起，Minecraft 专用 Java→C++ 翻译成为功能实现的主路径，翻译产物本机生成、不随包分发。
8. **UE 分发早验收**：M2 就要在**未安装 UE** 的干净机上跑通 Shipping 包，而不是等到产品化阶段。
9. **产品化后置**：正式 Launcher UI 属于 M4；此前只允许开发用 CLI 或最小调试启动器，不作为产品交付。
10. **普通用户不编译**：User Mode 使用官方预编译 Native Runtime；本地构建只属于 Developer Mode。
11. **版本解耦**：UE 升级与 Minecraft 版本升级是两条独立工作线。

## 2. 阶段总览（M3.5 为 M4 前的增补阶段）

| 阶段 | 目标 | 最重要的可见成果 | 主要依赖 |
|---|---|---|---|
| **M1 — C++ Native Gameplay Preview** | 尽早用 C++ Native Runtime 进入真实 Minecraft 世界 | 可运行的 C++ 原型：加载真实存档/区块，显示地形，第一人称移动与视角控制；无 JVM、无原版启动 | 无（仅需用户自有 Java Edition 文件） |
| **M2 — UE Native Rendering** | 用 Unreal Renderer 替换临时渲染方案 | 同一个 C++ Runtime 通过 UE 显示真实世界；Shipping 包在未安装 UE 的机器上运行 | M1 的 Runtime + Rendering Contract |
| **M3 — 完整游戏 + Converter** | 把原型发展为具备主要单机能力的 Native 游戏，并在 M1/M2 的 Converter 基础上升级为可重复使用的工具链 | 可玩的单机 Native Minecraft；对目标版本可重复分析、转换、生成、构建、验证 | M1；与 M2 可并行 |
| **M3.5 — 原生功能实现 + Java→C++ 转换** | 把 M3 的演示子集补成可玩的原生单机游戏；用转换器把 Java 玩法逻辑翻译为 C++ | `REIMNative.exe`（无 UE/JVM）；Tier A 功能覆盖；复刻原版菜单/创建世界/物品栏；修复 M2 水渲染；同一 DLL 可被 UE 可选加载 | M3 的 Runtime/Contract/Converter |
| **M4 — Launcher UI 与产品化** | 整合为普通用户可安装、可使用的产品 | 安装包、Launcher UI、实例/版本管理、Runtime 安装更新、启动与诊断；干净用户机验证 | M2 的 Shipping Runtime + M3.5 的可运行原生游戏 |

**阶段依赖**

```text
M1 ──→ M2 ─────────────────────┐
  │                             ├──→ M4（产品化验收）
  └──────→ M3 ──→ M3.5 ────────┘

M2 与 M3 在 M1 之后可以并行；M3.5 在 M3 之后；
M4 的 UI 骨架可在 M3.5 后期启动，但产品验收必须同时具备 M2 与 M3.5 的成果。
```

**不按严格串行处理的部分**

- M2 的 UE Host/Bridge 可以在 M1 后期用真实 Contract 数据并行开发；
- M3 的游戏系统可以在临时渲染器上先做逻辑与差分，不必等待 UE 渲染完成；
- Converter 从 M1 启动，M2 持续扩展，M3 完善并规模化；
- M3.5 的翻译器（字节码/IR/NJS）可在 M3 后期用真实类库做纵切；独立 exe 渲染器可与数据/翻译并行；
- M4 的 Launcher 框架与安装/更新机制可以在 M3.5 后期并行开发。

## 3. 第一阶段 — M1：C++ Native Gameplay Preview

### 3.1 目标

用 **C++ Native Runtime** 读取、解析和维护真实 Minecraft 游戏数据，进入用户自有的真实世界，看到实际区块与方块地形，并能以第一人称移动和观察。

这是项目第一个核心成果，也是后续所有工作的技术基线。它不追求完整游戏功能，也不要求 UE 渲染。

> 执行级任务拆分、C ABI/快照、Converter 产物格式与验收命令见 `M1_PLAN.md`。

### 3.2 工作内容

| 工作线 | 任务 | 说明 |
|---|---|---|
| **R — C++ Runtime 核心** | 世界状态、区块/区段、方块状态与调色板、玩家实体、相机、碰撞、固定 20 TPS 模拟循环 | 游戏逻辑全部在 C++ Runtime；不依赖 UE、不依赖 JVM |
| **C — Converter 启动** | Java Edition 文件摄取（version JSON/JAR/libraries/assets/存档）、版本与类依赖分析、数据提取、代表性样本转换与代码生成实验；建立 Converter ↔ C++ Runtime 的基本协作接口 | 真实产物直接驱动 Runtime；不把 Converter 推迟到 M3 |
| **C1 — 世界数据与生成表** | 解析 `level.dat`、Anvil `.mca`、区块 NBT；方块/注册表映射；导出/生成表 | 至少支持主世界一个维度；数据来自真实存档或真实生成输入 |
| **T — 临时 C++ Renderer** | GLFW + OpenGL（或 SDL3 + OpenGL）窗口、区块网格上传/绘制、纹理图集、视锥剔除、基础光照/雾、调试 HUD | 只消费 Runtime 快照；网格由 Runtime 生成，Renderer 不重建世界 |
| **I — 输入与相机** | 键鼠输入、第一人称相机、移动/跳跃/基础碰撞、可选调试视角 | 输入进入 Runtime，不由渲染器直接改世界 |
| **B — Rendering Contract 前置** | 定义版本化的世界/区块/玩家/相机快照与增量更新边界 | 同一 Contract 后续供 UE Renderer 使用；临时 Renderer 是它的第一个消费者 |
| **Q — 验证** | NBT/区块数据对照、加载截图、tick 计数、无 JVM 检查、10 分钟稳定性 | 不以“画面好看”为验收，先保证数据与状态真实 |

**数据来源规则**

- 只使用用户自有 Java Edition 文件（版本 JSON/JAR/libraries/assets/存档）作为输入与规格；
- JDK 25 仅允许在**离线数据生成/分析**阶段使用，Runtime 进程不得加载 JVM；
- 资源纹理优先从用户自有 JAR/资源包读取；缺失时可用占位色，但**地形数据不得伪造**；
- 方块/物品/实体 ID 与状态通过生成表或数据导出获得，不在代码中散落硬编码版本号。

### 3.3 允许与禁止

**允许**

- 使用 GLFW/SDL3 + OpenGL 的临时渲染方案；
- 只实现主世界、单一维度、有限渲染距离；
- 使用占位 UI、调试文字和简化光照；
- 使用离线生成表/导出数据辅助加载。

**禁止**

- 启动 `javaw.exe`、构造 Java classpath、加载 JVM 游戏；
- 用临时渲染器内置假地形、假区块或预生成演示场景冒充成果；
- 在渲染器中实现第二套世界/物理/方块逻辑；
- 把临时渲染器当作最终发布形态。

### 3.4 可见成果

- 一个可双击/命令行启动的 C++ 原型；
- Converter 能摄取/分析 26.3 文件，并产出供 Runtime 使用的数据/生成代码；
- 从用户自有 26.3 存档加载真实区块并显示地形；
- 第一人称摄像机与玩家实体（可用调试视角确认）；
- WASD/鼠标视角移动、基础碰撞与重力；
- 调试 HUD：坐标、区块、FPS、TPS、加载状态；
- 无 Java 进程、无 JVM 依赖的启动日志。

### 3.5 验收标准

1. 使用真实 26.3 存档启动，加载并显示实际区块与方块地形；
2. 第一人称相机可用，玩家可移动、转向、跳跃/下落，基础碰撞生效；
3. 运行时**没有** `javaw.exe`、JVM 或 classpath；
4. 临时 Renderer 只读取 Runtime 快照；替换/关闭 Renderer 不改变世界状态；
5. 模拟固定 20 TPS，渲染 FPS 可独立波动；
6. 连续运行 10 分钟无崩溃，日志可定位加载失败原因；
7. 抽查区块方块数据与原始 NBT/存档一致；
8. Runtime 的关键世界/注册表/方块数据来自 Converter 真实产物；临时手写/模拟数据仅限调试，且可追踪、可替换。

### 3.6 门禁 G1.5

| 条件 | 通过标准 | 不通过时的处理 |
|---|---|---|
| 真实世界加载 | 至少一个真实存档/区域完整加载，区块数据对照一致 | 先修数据管线，不进入 UE 渲染 |
| Converter 真实产物 | Runtime 的关键世界/注册表/方块数据来自 Converter | 补摄取/分析/数据生成，不用手写假数据推进 |
| 可操作性 | 第一人称移动/视角/碰撞可用 | 补齐 Runtime/输入，不用渲染器绕过 |
| 单一实现 | Runtime 与 Renderer 边界清晰，无假世界 | 重构 Contract/职责后再推进 |
| 无 JVM | 启动链无 Java/JVM | 视为产品边界失败，必须修复 |

**No-Go/改线**：若真实区块数据无法稳定加载，优先缩小维度/世界范围并加固数据管线；不得用演示世界替代。

### 3.7 前置与并行

- 前置：用户自有 26.3 文件；可选的离线数据生成环境；
- 可并行：Runtime 核心、Converter（摄取/分析/数据生成/样本转换）、临时 Renderer、Contract 定义、QA；
- 此阶段不要求 Launcher 产品 UI；开发用 CLI 启动即可。

## 4. 第二阶段 — M2：UE Native Rendering

### 4.1 目标

将 M1 的临时渲染方案替换为 Unreal Engine Renderer。C++ Runtime 继续负责游戏逻辑、世界状态和模拟；UE 只负责宿主与最终画面。

**前置依赖**：M1 的 Runtime 与 Rendering Contract 稳定；开发机具备 UE 5.8.4、MSVC/CMake 与打包环境。

> 执行级任务拆分、ABI v2/快照所有权、R0 渲染、Converter UE Adapter 集成/NativeBuild、Shipping 打包与验收命令见 `M2_PLAN.md`。

### 4.2 工作内容

| 工作线 | 任务 | 说明 |
|---|---|---|
| **U — UE Host** | UE 5.8.4 工程骨架、GameInstance/Subsystem、空舞台、窗口/输入/音频宿主 | 不把 Minecraft 世界对象变成 Actor/Component |
| **B — Rendering Bridge** | 实现 M1 定义的 Contract；快照/增量/池化缓冲；GT 与模拟线程同步 | C ABI/POD 只用于 Runtime Host ↔ Native DLL |
| **U2 — UE Renderer R0** | 区块几何、玩家、摄像机、基础纹理/光照/雾；可见性与批处理 | R0 只证明链路与数据，不做原版命令流/OpenGL 回放 |
| **S — Shipping** | UBT/UAT `BuildCookRun`；app-local VC++ 运行库；干净机验证 | 未安装 UE 的机器必须能运行 |
| **C — Converter 扩展** | 转换覆盖、数据生成、Native Adapter、Runtime Support、Patch；记录决策与生成物版本 | 与 UE 开发并行；持续用真实产物替换临时数据 |
| **T — 临时 Renderer 保留** | 作为开发调试/回归对照；是否保留到正式版本由实际情况决定 | 与 UE 共用同一 Runtime/Contract，不作为产品入口 |
| **Q — 验证** | R0 截图、20 TPS/FPS 独立、启动/退出、无 UE 依赖检查 | 为 M3/M4 建立渲染回归基线 |

### 4.3 关键约束

- 同一份 `mc_<version>.dll` 同时能被临时 Renderer 和 UE Host 驱动；
- UE 不接管游戏规则、物理、AI、世界模拟或网络权威；
- 模拟固定 20 TPS，UE 按 60/120/144+ FPS 消费不可变快照/增量；
- UE 资产引用通过编辑器/配置绑定，不在代码中硬编码资源路径；
- Converter 与 Runtime 的数据结构、接口和版本信息保持同源；生成代码不手改；
- Shipping 剥离 Editor/控制台/自动化依赖。

### 4.4 可见成果

- UE 5.8.4 工程与 `REIMRuntime.exe`；
- UE 中显示真实区块、玩家与摄像机；
- Converter 的覆盖范围与生成物清单（可重复产物）；
- 临时 Renderer 与 UE Renderer 显示同一世界状态；
- Shipping 打包产物与干净机运行记录；
- R0 截图与基本性能数据。

### 4.5 验收标准

1. 同一个 C++ Runtime 通过 UE 正常显示真实 Minecraft 世界；
2. 不依赖 Java Minecraft/JVM；
3. 20 TPS 模拟与渲染 FPS 解耦，帧率变化不影响世界 tick；
4. UE Shipping 包在**未安装 UE** 的干净 Windows 机器上启动并进入世界；
5. 临时 Renderer 仍可用于调试/回归，且不形成第二套游戏实现；
6. 启动、退出、崩溃日志可定位；
7. Runtime 使用的关键数据/生成代码来自 Converter 可重复产物，生成代码与 Runtime 接口版本一致。

### 4.6 门禁 G2

| 条件 | 通过标准 | 不通过时的处理 |
|---|---|---|
| 同 Runtime 双后端 | 同一 DLL/状态在临时 Renderer 与 UE 中表现一致 | 修 Contract/Bridge，不复制游戏逻辑 |
| Converter 覆盖 | 核心数据/生成代码由 Converter 可重复产出 | 补数据生成/Adapter，不回退到手写 |
| R0 渲染 | 区块/玩家/摄像机可辨认，截图基线建立 | 缩小渲染范围，优先保证数据链路 |
| Shipping 分发 | 干净机（无 UE）可运行 | 修运行库/打包/ABI，不把问题留给 M4 |
| 性能/线程 | 20 TPS 与 FPS 独立、稳定 | 调整快照/队列/线程模型 |

## 5. 第三阶段 — M3：完整游戏 + Converter

### 5.1 目标

把技术原型发展为具备**主要单机游戏能力**的 C++ Native Minecraft，并建立可持续使用的 Java Edition → C++ Native 转换工具链。

**前置依赖**：M1 的真实世界加载与 Runtime 稳定；Converter 已从 M1 启动并在 M2 持续扩展（M3 不是从零开始）。本阶段可与 M2 并行，但最终画面验收以 M2 的 UE Renderer 为准。

> 执行级任务拆分、Contract v3、可写存档/世界生成、R1/R2 渲染、Converter 数据规模化/差分/Patch、5 个执行阶段（原 10 个会话两两合并）与 G3 门禁见 `M3_PLAN.md`。

### 5.2 游戏线

- 方块交互：破坏、放置、选取、基础工具/耐久；
- 背包、物品、合成、熔炉、箱子；
- 玩家属性、生命/饥饿/经验、基础生物与战斗；
- 世界生成、区块加载/卸载、维度切换；
- UI、音频、资源包/数据包的必要功能；
- 存档读写与兼容（保留未知字段，不降级写）；
- 光照、天气、基础粒子等表现系统按缺口逐步补齐。

**范围原则**

- 以“主要单机玩法可玩”为目标，不承诺 26.3 全量行为/位级一致；
- 多人、Mod、生态能力默认不纳入本阶段，是否进入后续由实际缺口决定；
- 每个子系统明确支持范围与失败策略。

### 5.3 Converter 线

- 在 M1/M2 已有 Converter 能力上**完善并规模化**，不是从零开始，也不是重写；
- 版本分析：类/方法/字段清单、规范化字节码 hash、反射/Unsafe/JNI/依赖面报告；
- 数据生成与导出：注册表、方块状态、物品、实体、资源索引；
- 选择性翻译：按子系统选择源码/字节码/IR/代码生成/原生手写；
- Native Adapter：库替换、平台适配、渲染语义适配；
- Runtime Support：仅补齐必要的 Java 语义，不模拟完整 JVM；
- Patch 体系：按版本维护、可重放、可三路合并；
- 构建集成：产出 `mc_<version>.dll` 与 manifest；
- 差分验证：原版 oracle、tick/世界/包、存档往返、截图；
- 版本适配：新版本 diff → 决策 → 生成/翻译/Patch → 回归；
- 错误诊断：失败可定位到类/方法/Patch/构建阶段，保留中间产物与日志。

### 5.4 两条线如何配合

- Converter 与 Runtime 从 M1 起共同演进；生成代码、数据结构、运行时接口和版本信息必须一致；
- 不要求 Converter 先“通用化”才能开发游戏，但游戏所需的数据/代码必须优先由 Converter 产出；
- 每个游戏子系统先做最小数据导出/生成或原生实现，再把重复部分沉淀进 Converter；
- 每项转换决策记录在 `conversion-decisions/<profile>.md`，并附带验证方式；
- 不把项目做成通用 Java→C++ 编译器；JRT 只补齐必要的 Java 语义，不模拟完整 JVM；
- 生成代码不手改，修改进入 Patch。

### 5.5 可见成果

- 可玩的单机 Native Minecraft（主要玩法闭环）；

- 版本迁移与 Patch 重放记录。

## 5.5 增补阶段 — M3.5：原生功能实现与 Java→C++ 转换

> 详细工作包、DoD、验证与风险见 `M3_5_PLAN.md`。

### 5.5.1 为什么增加

M3 的实测结论是 **G3 FAIL**：它完成的是真实存档读取、20 TPS Runtime、三 Host、R0 UE 渲染、场景/差分/打包工具链，以及一个手写玩法子集（8 生物、137 配方、35 个原生物品行为等）。M3 把“完整”定义为 62 条场景闭环，并把翻译门禁判为 no-go，因此存档写入、光照、方块实体、通用模型、数据接管、多数生物/世界生成、UE R1/R2/UI/音频都没有落地。

M3.5 专门解决“功能没做”这件事：不再以场景数量代替功能覆盖，而是以 **Tier A 功能矩阵 + 可运行 exe + 存档往返 + 差分** 作为合同。

### 5.5.2 目标

1. 把 M3 的演示子集补成**可玩的原生单机游戏**，覆盖大部分 26.3 单机功能。
2. 建立 **Minecraft 专用 Java→C++ 转换器**：选择性全程序翻译 + 最小 Java 语义支持运行时（NJS）+ 原生平台/渲染/热路径替换。
3. 产出 **`REIMNative.exe`**：无 UE、无 JVM、无 JDK 即可运行；同一份逻辑仍可编译为 `mc_26.3.dll` 供 UE 可选加载。
4. **复刻原版单人 UI/菜单**：标题画面、世界列表、创建世界、生存/创造物品栏、容器、HUD、暂停/选项/死亡/加载；生存/创造/硬核；基础命令子集；语言 en_us/zh_cn；多人/Realms 显示但禁用。
5. **修复 M2 水渲染欠账**：原版水色/alpha、流动/水面动画、水下/双面/雾、waterlogging/流体高度、正确排序。
6. 建立功能覆盖、菜单/UI 复刻、翻译覆盖、存档往返、差分、无 JVM、可重复构建与性能门禁。

### 5.5.4 产物形态

```text
build/native/26.3/
  REIMNative.exe          # 原生宿主 + 游戏逻辑 + 渲染/UI/音频
  mc_26.3.dll             # 同一份游戏逻辑，供 UE 可选加载
  data/                   # manifest、翻译/覆盖报告
  generated/26.3/         # 用户本机由 jar 生成的数据/资产（不入库）
```

- 运行前置：Windows x64 + VC++ 运行库；不需要 UE/JDK/JVM/MSVC/CMake/VS。
- 翻译生成的 C++ 不提交、不随包分发；对外分发前法律评审或清洁室替换。
- UE Shipping 仍是可选最终表现宿主；M3.5 只要求 R0 不回归。

### 5.5.5 转换路线

```text
prepare → data → analyze → translate → build → verify
```

- **translate（新增）**：classfile/字节码解码 → 栈式 IR → C++ 生成 → NJS 绑定 → 原生替换表 → 覆盖报告。
- **NJS（不是 JVM）**：对象/数组/字符串/装箱、异常、类初始化、集合、Random/Math、lambda、NBT/Codec、堆与 GC；不做运行期类加载/字节码解释器。
- **翻译边界**：服务器/世界/玩法类优先翻译；客户端渲染/平台/网络走原生替换或拒绝；反射/Unsafe/ClassLoader 翻译期失败并记录。
- **生成代码**：不手改；修正进入版本化 Patch 或原生替换表；同输入两次生成/构建一致。
- **性能**：第一版正确性优先；热点（碰撞/物理/噪声/网格/存档/渲染）原生覆盖，必要时 IR 优化。

### 5.5.6 执行阶段

| 阶段 | 工作包 | 结束时的可运行结果 |
|---|---|---|
| S1 转换地基 | 基线/边界 + 字节码前端 + NJS + C++ 生成/构建 | 一个纵切（Brigadier/配方/战利品或世界生成）翻译后在 `REIMNative.exe` 跑通并与 oracle 对照 |
| S2 数据与欠账 | 数据接管 + 存档 + 光照 + 方块实体 + 通用模型 + 三维度 | 真实存档往返；全部内容加载 |
| S3 方块与世界 | 方块/物品行为 + 世界生成/结构 | 固定种子对照；结构可见 |
| S4 生存与实体 | 实体/AI/生成 + 生存/战斗 + 容器/配方/战利品 + 生存/创造/硬核 + 基础命令 | 游戏闭环：采集/创造→合成→建造→战斗→死亡/重生→基础命令→存档重载 |
| S5 表现与验收 | 水渲染 + 渲染/菜单/UI/音频 + 验证/差分 + 产物/文档 | 可玩 `REIMNative.exe` RC：标题→创建世界→游玩→物品栏/容器→保存退出→再进入；G3.5 通过或显式豁免 |

### 5.5.7 门禁 G3.5

1. **功能覆盖**：Tier A 矩阵逐项达标，核心内容无 `data_only`。
2. **可运行产物**：`REIMNative.exe` 在无 UE/JDK/MSVC/CMake 的机器上启动、进入标题画面、创建/选择世界、游玩、退出。
3. **菜单/UI 复刻**：标题画面→世界列表→创建世界→加载→游玩→生存/创造物品栏→容器→暂停→保存退出→再进入；键位/语言/资产回退/禁用项明确。
4. **水渲染**：水上/水下/流动/waterlogging/排序/群系水色通过固定相机截图与断言；不再是固定 0.72 alpha + section 排序。
5. **存档兼容**：Native 读→写→原版读；原版写→Native 读→写→原版读；未知字段保留。
6. **翻译覆盖**：边界 manifest 与覆盖报告完整；无运行期类加载/字节码解释器。
7. **差分有效**：世界/方块更新/光照/配方/战利品/实体/存档有 oracle 或基线，阈值冻结。
8. **可重复**：同输入/同工具两次生成/构建一致。
9. **无 JVM**：exe/Runtime 无 java/javaw/JVM/classpath；无 JVM 导入。
10. **性能/稳定**：20 TPS ±0.2；渲染 FPS 目标；30 分钟无泄漏/无崩溃。
11. **法律/资产**：生成物不提交/不随包分发；包内无 Mojang 资产/jar。
12. **用户试玩**：核心闭环可完成，问题清单记录。

`not_run` 不计为通过；未执行项必须显式写 `not_run` 或豁免。

### 5.5.8 与 M3 / M4 的关系

## 7. 阶段依赖与并行轨道

| 轨道 | 内容 | 主要阶段 | 可独立推进的时点 |
|---|---|---|---|
| **R — C++ Runtime** | 世界状态/模拟/玩家/物理/存档/协议 | M1 → M3 | 第一天起，关键路径 |

| **J — Java→C++ 翻译** | 字节码前端/IR、C++ 生成、NJS 支持运行时、原生替换、覆盖报告 | M3.5 | M3 后期做纵切；与数据/渲染并行 |

- M4：L + Q 为主；R/C/U 进入维护与问题修复。

## 8. 版本更新列车（M3 起成为常态）

> M1 起即使用 Converter 的真实产物（摄取/分析/数据生成/样本转换）；完整流水线随 M1→M3 逐步扩展。

```text
新 Minecraft 版本
      ↓
D0 检测/摄取
  version manifest → version JSON → client/server JAR → libraries → assets
      ↓
D1 准备（JDK 25，仅离线阶段）
  数据生成器 --reports；Java 导出器；资源/语言/模型/声音索引
      ↓
D2 差异分析
  类/方法/字段 + 规范化字节码 hash；协议/注册表/数据包/资源包 diff
      ↓
D3 分诊
  每个子系统选择：代码生成 / 选择性翻译 / 原生手写 / 库替换 / Patch
      ↓
D4 产出
  生成表/常量/codec；翻译纯逻辑；手写渲染/平台/热路径；Patch；库适配
      ↓
D5 构建
  Developer Mode：CMake/MSVC → mc_<version>.dll；CI：UBT → UE Runtime
  User Mode：直接分发/更新官方预编译 Native Runtime
      ↓
D6 差分测试
  server/client oracle、tick/world/packet、存档往返、资源包、截图
      ↓
D7 渲染验证
  R0/R1/R2/R3 截图、性能、OIT/透明、资源包
      ↓
D8 发布
  UE Shipping 包 + manifest + 兼容矩阵；Launcher 更新
```

**规则**

- 同输入/同工具/Patch 应可复现；生成代码固定遍历顺序/命名；
- 失败保留中间产物与日志，错误定位到类/方法/Patch/构建阶段；
- 不把反编译源码提交/发布；只保留必要的符号/摘要/补丁；
- UE 升级走独立分支，不与 Minecraft 版本升级绑定。

## 10. 风险与不确定性

| 风险 | 级别 | 影响 | 缓解 |
|---|---|---|---|
| 真实世界数据加载（NBT/Anvil/调色板/注册表）比预期复杂 | **高** | M1 无法按预期进入真实世界 | 先支持单存档/单维度；数据管线独立验证；对照原版工具 |
| 临时 Renderer 被误当产品/演示世界 | **高** | 成果失真，后续返工 | 验收强制“无假世界”；Renderer 只读 Runtime；不进入发布 |
| 临时 Renderer 与 UE Renderer 形成两套实现 | **高** | 行为分叉、维护爆炸 | 共用 Contract/快照；同一 DLL；回归截图对照 |
| Native 化自动化率不达预期 | **极高** | 产品核心不成立/工期失控 | P0-A/B/C 度量；范围收缩；原生适配兜底 |
| Java→C++ 翻译闭包/语义缺口 | **极高** | 无法覆盖大部分功能或行为偏差 | 入口闭包裁剪；NJS 对照；不支持项翻译期失败；差分 oracle |
| 生成代码性能不足 | 高 | 20 TPS/FPS 不达标 | 正确性优先；热点原生覆盖；IR 优化；profile |
| 独立 exe 渲染器工作量 | 高 | 画面不可用/拖慢功能 | 升级 Preview 渲染器；先可玩后保真；UE 可选 |
| 复刻原版菜单/UI 范围 | 高 | 标题/创建世界/物品栏/选项做不完 | 明确屏幕清单；先流程/布局/交互，再做逐像素保真 |
| 水渲染（M2 欠账） | 高 | 水下/流动/排序仍错误 | M35-G1 专项；独立 water pass；固定相机回归 |
| 翻译产物法律风险 | 极高 | 无法分发 | 生成物不提交/不随包；本机 Developer Mode；分发前评审 |
| oracle 不被批准 | 中 | 差分覆盖不足 | 静态 fixtures；显式记录降级 |
| Java 语义偏差（GC/异常/线程/集合/浮点） | 高 | 行为不一致/难复现 | JRT 最小面；差分；固定数学/顺序 |
| 渲染覆盖/保真/性能不足 | 高 | 视觉差异/帧率不达标 | R0→R1→R2→R3；截图门禁；parity profile；OIT 专项 |
| 世界生成/红石/AI 广度失控 | 高 | 长期无法覆盖 | 纵向切片；M3 明确支持范围；剩余缺口后置 |
| 版本更新频繁 | 高 | 维护成本上升 | diff/生成/Patch/差分工具链；单 profile 起步 |
| 法律/衍生作品/资产/UE 许可 | 极高 | 无法发布/下架/诉讼 | 用户自有输入；官方预编译 Runtime 法律评审；不分发 Mojang 代码/资产 |
| 产品化拖到 M4 才发现依赖问题 | 中 | 返工 | M2 起持续验证 Shipping/运行库/启动链路 |

## 11. M4 之后

以下方向根据实际缺口决定是否立项，**不提前承诺**，也不写成首版必须完成的内容：

- 多人游戏与原版服务器互通（协议、登录、聊天签名、专用服务器）；
- Mod/Native 扩展生态与内容 API；
- 性能优化、更高阶 UE 渲染（LOD/RT/PBR/更远视距）；
- Minecraft 新版本适配与自动迁移；
- 自动化 CI、发布流水线、兼容性矩阵扩展；
- 回放/录制、开发者工具与诊断增强。

进入这些方向前，应先有 M1–M4（含 M3.5）的实际缺口和用户需求作为依据。

---

## 12. 明确不属于首版

- Java Mod/Mixin/Forge/Fabric 兼容；
- OptiFine/Iris shaderpack；
- 完整 DFU 旧存档原生迁移；
- 完整世界生成/红石/AI/命令的位级一致；
- 移动端/主机端；
- 通用 Java→C++ 编译器产品；
- 多人/服务器/生态能力的首版承诺；
- 普通用户本地编译 C++ 的路径。

M3.5 的 Minecraft 专用翻译属于功能实现手段，不改变“不做通用 Java→C++ 编译器产品”的边界；翻译产物不作为对外分发内容，分发前必须法律评审。

## 13. 关于工期

本文不给出日期或精确工期。个人开发的实际节奏取决于数据面复杂度、Converter 自动化率、渲染覆盖和可用时间；阶段推进只以验收标准与门禁为准。若后续需要估算，应标注为**个人开发的粗略量级**，并与阶段验收条件分开。
