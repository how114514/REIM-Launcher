# Conversion decisions — Minecraft Java Edition 26.3

> Audit record for M2 (ROADMAP §5, M2-E8). Decisions describe what the
> Converter and Runtime actually do; they do not claim Java rendering
> translation or full conversion coverage.

## 1. Data generation route

- Block states, models, face sprites/tints and block textures are derived from
  the user's own 26.3 `client.jar` assets by `reim-convert extract`.
- The vanilla data generator reports directory is not started (this
  environment does not start Minecraft/Java); the gap is recorded in
  `generated/26.3/extraction_report.json`.
- `extract` emits schema v2: `manifest.json` (format 2, ABI 2, input and
  generated hashes, atlas descriptor, capabilities), `blocks.json` (stable
  sort, material class, face-level sprite/tint), `textures.json` (atlas tile
  metadata, nearest/no-mip sampling) and `debug_inputs.json` (absolute input
  paths, local diagnostics only; excluded from the manifest and never packed).
- Generated files are never hand-edited. The Runtime and UE Host reject a
  manifest whose schema, profile, ABI or file hashes do not match.

## 2. UE rendering is a Native Adapter

- The UE runtime (`runtime/host`) is a **pinned native adapter**, not a
  translation of Java's render pipeline. There is no Java→UE shader/material/
  RenderType conversion, no command replay and no second world implementation.
- Converter responsibilities are pin, combine, validate and package:
  `converter/adapters/ue/adapter_pin.json` pins adapter identity/version,
  UE 5.8.4, ABI 2 and R0; `generate_ue_adapter.py` records the hashes of the
  adapter's uproject/Config/Content/plugin assets into `ue_adapter.json`.
- The Bridge compiles the same pin (`ReimAdapterPin.h`); a mismatch between the
  descriptor, the pin and the running UE version is a startup failure.

## 3. Contract and version binding

- Rendering Contract v2 (`runtime/contract/reim_abi.h`, `reim_render.h`) is
  frozen for M2: host-owned frame blobs, interpolation snapshots, `get_asset`,
  `get_runtime_info`, render level 0.
- `reim-convert package` binds the exact `mc_26.3.dll` hash, the generated
  manifest hash and the adapter descriptor hash into `native_version.json`
  plus a deterministic `verification.json`.
- `reim-convert assemble` combines the UE Runtime package and NativeVersion
  into a NativeBuild and records all three directory digests in
  `native_build.json`.
- The UE Host loads only `<native_version_path>/mc_26.3.dll`; `dll_path` is
  ignored. At startup it verifies the DLL hash, manifest hash, adapter file
  hash, adapter identity and UE version, and after `create` it checks that the
  Runtime accepted the same manifest hash. Manual assembly does not pass
  (M2-E9).

## 4. R0 rendering scope

- R0 renders chunk geometry supplied by the C++ mesher, an atlas texture from
  `get_asset`, baked vertex light/tint with a directional-light fallback,
  distance fog, sky colour, a debug player proxy and a Runtime-driven camera.
- The S1 implementation uses the plan-permitted degradation:
  `FLocalVertexFactory` with baked vertex colour instead of a custom vertex
  factory. R1 restores the custom VF. This is not a Java shader translation.
- Entities, block entities, particles, weather, audio, post-processing, OIT
  and the full Minecraft UI are out of scope for M2.

## 5. Unsupported / not done

- No JRT expansion, bytecode translation or full DFU adaptation in M2.
- Non-full-cube block models are not meshed (M1 known limitation).
- Single dimension, read-only world, no save writes.
- DX12 is the acceptance path (SM5 observed in S1); DX11 is a smoke item.
- M2 packages are internal acceptance artifacts only; Mojang assets are never
  redistributed.

## 6. S4 visual-correctness extensions (2026-11-21)

- `blocks.json` (format 2, backwards-compatible optional keys) gains:
  `tint_kinds` (per face: `grass`/`foliage`/`water`), `variants` (canonical
  state key such as `snowy=true` or `layers=2` with its own sprite/tint/geometry
  override) and `geometry` (explicit quads for non-cube models: snow layers,
  crosses, ≤2-element boxes). Existing fields keep their meaning.
- `biome_tints.json` (new generated file, listed in `manifest.json`
  `generated[]`) maps each biome to grass/foliage/water colours computed from
  the user's `client.jar` biome JSON and `textures/colormap/{grass,foliage}.png`.
  The Runtime tints grass/foliage/water vertices per block position; missing
  tables fall back to fixed vanilla defaults.
- Model coverage is deliberately bounded: only models with at most two elements
  and no non-cross rotation become geometry. Stairs, fences, doors, walls and
  other multi-element/rotated models remain `skip` until R1; they are not
  approximated.
- These are data/renderer extensions. The ABI v2 vertex layout, frame
  ownership, coordinates and NativeVersion/NativeBuild schemas are unchanged.

## 7. M3 4B toolchain decisions (2026-11-21)

- **Data route.** `reim-convert data` runs the official offline data generator
  with the user's server JAR (`-DbundlerMainClass=net.minecraft.data.Main
  --reports`), unpacks the bundler's inner server JAR (`data/minecraft/**`) and
  copies the M3 sound/lang/font assets from the client asset index. This is an
  offline JDK tool; no Minecraft client or server is started and the Runtime
  never loads a JVM.
- **Schema v3.** `extract` now emits manifest format 3 / ABI 3 with
  `items/entities/models/recipes/loot_tables/tags/worldgen/sounds/lang/
  coverage_report`. Block state ids come from `reports/blocks.json`; visual
  geometry still comes from `client.jar` blockstates/models. The block/item
  atlases are built from the real textures; 7 non-16×16 item textures are
  listed as skipped rather than scaled silently.
- **Source matrix honesty.** Entity models/AI/spawn rules, block behaviour,
  item attributes, and the worldgen profile are labeled as Java-code sources.
  `data_only` items are ingested and diffable but do not add gameplay. The
  Runtime continues to use the native recipe/loot subset; generated recipes/loot
  are not claimed as gameplay coverage.
- **Analysis.** The offline analyzer now emits class/method/field lists,
  normalized per-class bytecode hashes, a per-class dependency graph and a
  reflection/Unsafe/JNI/ClassLoader surface report. Two runs are byte-identical.
- **Diff/patch/ledger.** `diff` produces per-subsystem added/removed/changed
  hashes with work items; `ledger` maps Java symbols to native/generated/
  analysis owners with evidence-based status; `patch` replays a versioned set,
  applies entries atomically, and performs JSON three-way merges with explicit
  conflicts. The 26.3 patch set is empty until a real second version (or an
  approved synthetic delta) is available.
- **Not done.** Version-upgrade drill (L7) belongs to stage 5A and remains
  `not_run` (no adjacent second version; a synthetic delta was not approved).
  The translation/JRT gate (M3-M) was decided **no-go** in stage 5A (§8). UE
  R0 runtime negotiation is now verified after starting the UE Zen server;
  R1/R2/UI/entity/audio Host integration is still not implemented (§8).

## 8. M3 5A translation/JRT gate (2026-11-21)

**Decision: no-go for selective Java translation and JRT in M3.** No code is
translated, no JRT surface is introduced, and the Runtime remains JVM-free.

Candidate review (M3-M1):

| Candidate | M3 relevance | Decision | Reason |
|---|---|---|---|
| DataFixerUpper Codec/DynamicOps | Old-save upgrade and JSON codec parity | **no-go** | M3 uses canonical generated JSON loaded by native parsers; DFU rules in 26.3 are compiled classes, not data. Full DFU is explicitly out of scope (`ROADMAP` D-16). Translating Codec/DynamicOps would add JRT semantics (generics, exceptions, lambdas, optional) with no measured data-loading bottleneck. |
| Brigadier | Commands/command suggestions | **no-go (scope)** | Commands are not in M3 (`M3_PLAN §0.2`/§1.2); no consumer. |
| Other pure logic (recipe/loot matching, NBT codecs) | Gameplay/data loading | **no-go** | Already native or data-driven; replacing working native tables with translated code adds maintenance and diff risk without a gate benefit. |

Gate evidence:

- Data route: `reim-convert data/extract` produces the §9.2 schema-v3 files;
  the Runtime loads them directly (`runtime/mc-native/data/`). No subsystem in
  M3 is blocked on Java-only semantics.
- Source matrix: Java-code-sourced areas (entity models/AI, block behaviour,
  item attributes, worldgen profile) are recorded in the port ledger and are
  native by design, not pretending to be data extraction (`§7`).
- JRT face: **0**. `python tools/m3-jrt-audit.py` scans the Runtime/Preview/
  headless/Contract sources and Runtime CMake targets: 86 files, 0 non-comment
  JVM/JNI/JRT/bytecode hits, 0 JVM link libraries
  (`build/m3/reports/jrt-audit.json`). No Java process, class loader or
  bytecode interpreter exists in the Runtime.
- Offline JDK use remains confined to the Converter/analyzer/data generator and
  does not enter the Runtime or any shipped package.

Alternatives if a future version needs a translated subsystem: native tables,
generated data, or a versioned Patch first; re-open the gate with a measured
bottleneck and a bounded JRT surface plus an exit plan. This decision does not
block L7 or any other M3 work package.

**UE R0 runtime note (same session):** the Zen storage-server failure was an
environment problem (no `zenserver.exe` listening). Starting UE's Zen server
made the R0 Host start, load the real 26.3 world, render and exit; the adapter
descriptor format check in the Bridge had to be updated from 2 to the schema-v3
format 3. This verifies the M3 A3 three-Host path for R0 only. R1/R2, entity,
UI and audio consumption are still absent from the UE Host and are not claimed.
